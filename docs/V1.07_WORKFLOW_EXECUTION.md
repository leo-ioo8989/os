# LEO OS V1.07 — Workflow ↔ Job Durable Execution

## Scope

V1.07 is Phase 1 control-plane infrastructure for the private/internal LEO OS system. It coordinates durable Objective → Workflow → Task → Job → Worker → Execution/Approval state. It does not execute external actions and does not introduce AI/model providers or integrations.

## State model

Workflow lifecycle:

```text
PENDING → RUNNING
RUNNING → WAITING_APPROVAL | PAUSED | BLOCKED | FAILED | COMPLETED | CANCELLED
WAITING_APPROVAL → RUNNING | PAUSED | FAILED | CANCELLED
PAUSED → RUNNING | CANCELLED
BLOCKED → RUNNING | CANCELLED
FAILED → RUNNING | CANCELLED
COMPLETED / CANCELLED → terminal
```

Job lifecycle remains the V1.05/V1.06 model:

```text
QUEUED → CLAIMED → RUNNING
RUNNING → SUCCEEDED | WAITING_APPROVAL | RETRY_QUEUED | FAILED | CANCELLED
WAITING_APPROVAL → RETRY_QUEUED | FAILED | CANCELLED
RETRY_QUEUED → CLAIMED
SUCCEEDED / FAILED / CANCELLED → terminal
```

## Durable coordination

A Workflow persists both `currentTaskId` and `currentJobId`. A Job may carry an organization-scoped `idempotencyKey`. Workflow progression is performed inside the same serializable transaction as the Job result when the Job repository processes success/failure/approval transitions.

A successful current Job:

1. remains durably `SUCCEEDED`;
2. completes its Task;
3. evaluates dependency readiness from the existing Task graph;
4. selects the next task deterministically;
5. creates or retrieves a queued Job using an idempotency key;
6. persists Workflow current task/job pointers;
7. records audit events.

The next Job is only queued. It is not implicitly executed.

## Deterministic next-task policy

Tasks must first be dependency-ready. Because the existing Task model has no priority field, ties are resolved by stable Task ID ordering. The policy is independent of worker timing, process memory and incidental database ordering.

## Retry / approval

Retryable Job failures remain `RETRY_QUEUED` and preserve a resumable Workflow. Exhausted/permanent failures move the Job to `FAILED` and the relevant Workflow/Task to failed state.

A Job requiring approval persists `WAITING_APPROVAL`. Approval remains separate from execution and keeps its V1.06 fingerprint/requester/policy/expiration/single-use binding. Approved resolution queues the Job for a future authenticated Worker claim; rejected resolution fails the Job/Workflow.

## Restart and reconciliation

Reconciliation derives decisions from durable state. Safe repairs include:

- terminal Workflow with executable Jobs → cancel those Jobs;
- succeeded current Job with missing Workflow advancement → advance the Workflow transactionally;
- consumed approval with waiting Job → queue the Job for resumption;
- missing current-job pointer with exactly one Job for the current Task → restore the pointer.

Ambiguous conditions are not guessed. Examples include multiple Jobs for one current Task or an unresolved current-job pointer. Those states are returned for human intervention and audited.

Expired active Job leases continue through the existing V1.05 stale-lease recovery path.

## Cancellation

Workflow cancellation atomically cancels executable child Jobs and nonterminal Tasks. Terminal Workflows do not resume and reconciliation prevents remaining executable Jobs from continuing.

## Checkpoints

The existing Checkpoint model remains the resumable execution snapshot boundary. Checkpoints require organization and active-worker ownership, monotonically advance per Job, are unavailable after terminal execution, and use the existing recursive sensitive-key redaction before persistence.

## Security boundaries

- Every Workflow/Job lookup is organization-scoped.
- Parent Objective/Task/Workflow/Worker references are validated against the same organization.
- Worker lifecycle and lease ownership checks remain enforced by JobRepository.
- Privileged action authorization remains centralized in the V1.06 Execution Gateway.
- Approval is never treated as execution.
- Terminal states reject resurrection.
- Audit/checkpoint metadata is sanitized; credentials, tokens and secrets are not persisted there.
- Serializable transactions are used for coordination mutations.

## Idempotency boundary

V1.07 does not claim mathematically perfect exactly-once external execution. It implements practical exactly-once-like control-plane progression: stable idempotency keys, explicit current-job pointers, serializable transactions and deterministic transition rejection. External action execution is still absent.
