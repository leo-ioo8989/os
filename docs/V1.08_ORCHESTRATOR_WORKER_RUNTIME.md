# LEO OS V1.08 — Orchestrator + Worker Runtime

## Scope

Callable Phase 1 control-plane runtime only. No AI agents, model providers, MCP, external APIs, browser automation, autonomous external actions, or Command Center UI.

## Architecture

```text
Objective → Workflow → deterministic dependency selection → Job
→ Job Dispatcher → trusted Worker → Execution Gateway
→ controlled internal Handler Registry → result validation
→ JobService/JobRepository → existing V1.07 workflow advancement
→ next task/job or terminal state
```

`Orchestrator.orchestrate(organizationId, workflowId)` is a bounded callable cycle. It reconciles durable state, creates the next dependency-ready Job through `ensureWorkflowJob`, dispatches only jobs for the requested workflow, selects ACTIVE workers deterministically by Worker ID, requires the task capability, invokes Worker Runtime, and returns structured counts plus a deterministic stop reason. There is no infinite daemon.

## Handler registry

Task metadata declares `handlerId`, `capability`, `action`, `target`, `risk`, and `parameters`. The declaration must match a registered handler. Current handlers are internal and test-safe: `internal.noop`, `internal.calculate`, `internal.fail`, and `internal.checkpoint`. They cannot execute shell commands, arbitrary code, network calls, or external integrations.

## Worker lifecycle

```text
QUEUED/RETRY_QUEUED → atomic claim → authentication → RUNNING
→ Execution Gateway → registered handler → validated result
→ SUCCEEDED / FAILED / RETRY_QUEUED / WAITING_APPROVAL
```

Worker Runtime uses `JobService` for durable mutations, heartbeats and checkpoints. It never executes arbitrary job payload code.

## Approval

High-risk execution remains behind the existing V1.06 Execution Gateway. `REQUIRES_APPROVAL` moves the Job to `WAITING_APPROVAL` without executing a handler. Approved execution may be resumed with an approval ID and injected approval consumer; the existing gateway remains responsible for fingerprint, worker, organization, policy and expiration binding.

## Concurrency and idempotency

Workflow-generated Jobs use `workflow:<workflowId>:task:<taskId>`. The existing organization-scoped unique database constraint remains authoritative. Job claim, workflow reconciliation and Job creation rely on PostgreSQL transactions rather than process-local locks.

A V1.08 hardening fix also rejects expired Worker leases during owned Job transitions, preventing stale workers from starting or completing an expired lease.

## Failure and recovery

Existing `retryDecision`, persisted `maxAttempts`, stale-lease recovery and V1.07 reconciliation remain authoritative. V1.08 does not introduce infinite retries or in-memory correctness state.

## Observability and security

Orchestration results report workflow before/after state, ready work, created/dispatched/completed/failed/retrying/approval-blocked Jobs, selected workers, unavailable workers and a deterministic stop reason. Existing audit redaction remains in force.

Source-level security review covers organization scoping, ACTIVE worker checks, credential authentication, capability matching, handler allowlisting, Execution Gateway enforcement, approval binding, idempotency, lease expiry and terminal-state protection.
