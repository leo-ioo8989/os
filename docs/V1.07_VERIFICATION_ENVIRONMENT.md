# LEO OS V1.07 Verification Environment

This document defines the disposable, repository-local runtime used to verify V1.07 against real PostgreSQL. Creating this environment does **not** mean V1.07 is verified.

## Runtime baseline

- Package manager: pnpm 10.15.0 (declared by the root `package.json`).
- Node.js: the verification container/CI uses Node.js 22. The repository targets ES2022 and currently does not declare an `engines` field.
- Prisma: `@prisma/client` and `prisma` 6.15.x range.
- Database: PostgreSQL 16.
- Test runner: Node.js built-in `node:test`, invoked through `tsx`.
- Prisma datasource: PostgreSQL via `DATABASE_URL`.
- Test database: `founder_os_test`.
- Local verification port: `55432`.

## Local PostgreSQL

Docker is the supported local runtime because it keeps the database disposable and does not require a paid service.

Start:

```bash
pnpm db:start
```

Check:

```bash
pnpm db:status
```

Stop and keep data:

```bash
pnpm db:stop
```

Reset the disposable database and volume:

```bash
pnpm db:reset
```

The compose file uses PostgreSQL's local `trust` authentication inside the isolated container. No password or production credential is stored in the repository. The test connection is:

```text
postgresql://postgres@localhost:55432/founder_os_test
```

For a shell/session, copy `verification.env.example` to an ignored local environment file or export `DATABASE_URL` directly. Do not commit `.env` files or production credentials.

## Prisma verification

After dependencies are installed and PostgreSQL is running:

```bash
pnpm db:generate
pnpm db:validate
pnpm db:migrate
pnpm db:smoke
```

`db:migrate` uses `prisma migrate deploy`, so the complete committed migration chain is applied without creating a new migration. `db:reset` is intentionally destructive and is only for the disposable verification database.

Database tests:

Real PostgreSQL integration tests:

```bash

```

Full existing workspace test suite:

```bash

```

Typecheck and lint:

```bash

pnpm lint
```

The V1.07 verification sequence is:

```bash
pnpm verify:v107
```

This command generates Prisma, validates the schema, applies migrations, typechecks, lints, runs the existing unit suites and runs the PostgreSQL integration suite. It does not itself start PostgreSQL.

## Current integration coverage

`packages/db/test/v107-runtime.test.ts` is intentionally a real-database test. It verifies:

- V1.07 `Workflow.currentJobId` exists.
- V1.07 `Job.idempotencyKey` exists.
- `WorkflowStatus.BLOCKED` exists in PostgreSQL.
- identical idempotency keys deduplicate inside one organization.
- the same idempotency key remains valid independently in another organization.
- workflow advancement creates a durable, non-null workflow Job idempotency key.

This is an initial runtime harness, not the complete V1.07 concurrency/recovery/security certification suite. Those tests must be added and executed before claiming V1.07 verified.

## CI

`.github/workflows/v107-verification.yml` runs the same Phase 1 database-backed baseline on GitHub Actions using PostgreSQL 16. It performs dependency installation, Prisma generation/validation/migration, database smoke, typecheck, lint, unit tests and integration tests.

The repository currently has no committed `pnpm-lock.yaml`. CI therefore uses `pnpm install --no-frozen-lockfile`. Until a lockfile is generated and committed, dependency resolution is reproducible at the declared package-manager/toolchain level but not fully dependency-lockfile deterministic.

## Required future V1.07 verification

The environment is ready for, but does not yet prove, the following runtime suites:

- two-worker Job claim race
- simultaneous Job completion/Workflow advancement
- concurrent idempotent Job creation
- concurrent approval decisions and approval consumption
- worker lease and checkpoint ownership races
- interrupted/stale/expired Job recovery
- Workflow reconciliation and repeated reconciliation
- missing `currentJobId` recovery
- approval-blocked recovery
- terminal Workflow/Job behavior
- cross-organization and forged-reference rejection
- approval substitution/replay rejection
- suspended/revoked/stale worker rejection
- transaction failure injection and rollback
- complete Worker → Job → Execution Gateway → Approval → Workflow continuation
- migration/index/constraint inspection beyond the initial runtime assertions

No external service, AI provider, MCP server, integration, browser automation, autonomous action or Command Center UI is part of this environment.
